# 會議室門口顯示系統設計

日期：2026-09-18

## 背景與目標

社區有 5 間會議室，門口各裝有一台直立式螢幕（1080×1920），目前指向一套 2014 年的老舊物業管理系統「超媒體管家」（172.18.0.251）提供的公告看板頁面（`room01.html`~`room05.html`）。該系統的佔用狀態資料（`list.php` + `TranPackage.php`）需要登入 session 才有即時資料，匿名連線抓不到，且 `list.php` 不論帶什麼參數都只回傳「會議室A」一間，無法可靠取得其餘 4 間的即時狀態。

**決策**：不再嘗試整合舊系統，改為在本專案（社區佈告欄系統）內完全自建一套會議室門口顯示系統，資料由管理後台自行維護，與舊系統完全脫鉤。既有的物理螢幕硬體不需更動，只需把每台螢幕指向的網址從舊系統改成新網址。

## 目標

- 5 間會議室門口的螢幕，各自顯示「本房間目前使用中/未使用」與「本房間今日剩餘（尚未到期）的預約」
- 同時輪播顯示會議室專用公告（跟大廳既有公告分開管理）
- 管理後台能新增/編輯/刪除預約，並管理會議室專用公告

## 非目標（本次不做）

- 不整合舊系統（172.18.0.251）的任何資料或功能
- 不做住戶自助預約介面，預約僅能由管理後台新增（住戶電話/現場要求，櫃台人員代為登記）
- 不做「5 間會議室一次看」的匯總畫面（大廳或後台首頁），僅做 5 台門口螢幕各自的顯示頁 + 後台既有的預約列表
- 不處理跨房間資源衝突以外的驗證（主旨、聯絡人欄位不強制必填）

## 架構

**做法**：共用引擎 + 5 個極簡入口檔案（相較於「單頁+網址參數」或「5 份完整複製」，這個做法維持既有專案「一個資料夾對應一台實體螢幕」的慣例，同時邏輯只維護一份）。

```
shared/roomBoard.js              ← 新增：顯示邏輯全部在這裡（唯一維護點）
renderer/room-a/index.html       ← 新增：ROOM_ID='A'，載入 roomBoard.js
renderer/room-b/index.html       ← 新增：ROOM_ID='B'
renderer/room-c/index.html       ← 新增：ROOM_ID='C'
renderer/room-d/index.html       ← 新增：ROOM_ID='D'
renderer/room-e/index.html       ← 新增：ROOM_ID='E'
shared/api.js                    ← 修改：DATA_KEYS 加入 meetings（已存在，沿用）、meetingAnnouncements（新增）
renderer/admin/index.html        ← 修改：補完會議室預約分頁、新增會議室公告分頁、房間清單維護
```

## 資料結構

### `meetings`（延續既有資料鍵，修正 rooms 的形狀）

```js
meetings: {
  rooms: [
    { id:'A', name:'會議室A', capacity: 40 },
    { id:'B', name:'會議室B', capacity: 20 },
    { id:'C', name:'會議室C', capacity: 20 },
    { id:'D', name:'會議室D', capacity: 10 },
    { id:'E', name:'會議室E', capacity: 10 }
  ],
  bookings: [
    { id: 1758... /* Date.now() */, roomId:'A', date:'2026-09-20', startTime:'14:00', endTime:'15:30', topic:'管委會議', person:'王小姐' }
  ]
}
```

- `rooms[].id` 對應 5 個入口檔案各自的 `ROOM_ID`，是穩定識別碼，房間改名不影響資料關聯
- `date` 為西元 `YYYY-MM-DD`（`<input type="date">` 原生格式，不需民國年轉換）
- `startTime`/`endTime` 為 `HH:MM`（`<input type="time">` 原生格式）
- `topic`/`person` 欄位名稱沿用既有但未接上邏輯的 CSS class（`.booking-topic`、`.booking-person`）

### `meetingAnnouncements`（新增資料鍵）

```js
meetingAnnouncements: { marquee:'', list: [ { id, title, type, duration, content, imageUrl, alwaysValid, startDate, startTime, endDate, endTime, date } ] }
```

欄位形狀與既有 `announcements`／`announcements_v` 完全相同，讓既有的公告編輯視窗（即時預覽、樣式工具列、圖片上傳、日期範圍）可以直接擴充支援第三種資料集，不必新建編輯介面。`shared/api.js` 的 `DATA_KEYS` 需加入 `'meetingAnnouncements'`，`DEFAULTS.meetingAnnouncements = { marquee:'', list:[] }`。

### 房間目前狀態：即時運算，不落地存欄位

用「現在時間」比對該房間今天的 `bookings`：若存在一筆 `date === 今天 && startTime <= 現在 < endTime`，即為使用中（顯示該筆 `topic`）；否則未使用。管理員只需維護預約紀錄，狀態永遠自動正確。

## 管理後台

### 會議室預約分頁（補完既有擱置的骨架）

- 側邊選單新增「🏢 會議室預約」（目前完全沒有入口）
- 日期選擇器 + 房間卡片，每張卡片列出**當天該房間的所有預約時段**（現有 `renderBookings()` 目前只渲染房間名稱、無預約內容，需補上）
- 「＋ 新增預約」開啟編輯視窗：選房間、日期、起訖時間、主旨、聯絡人。這是目前程式碼裡完全不存在、點擊會直接報錯的 `openBookModal()`，需要實作
- 新增/編輯時做**同房間同時段重疊檢查**：與同一 `roomId`、同一 `date` 的既有預約比對，重疊判斷公式為 `新.startTime < 既有.endTime && 新.endTime > 既有.startTime`（標準區間重疊判斷，任一方向有重疊即擋下並提示，編輯既有預約時排除自己那一筆）
- 編輯／刪除既有預約

### 會議室公告分頁（新增）

- 側邊選單新增「📋 會議室公告」
- UI 結構比照既有「公告管理」／「公告管理（直立）」（列表 + 新增按鈕）
- 「編輯」開啟既有公告編輯視窗，`_annDataset` 傳入新值 `'meetingAnnouncements'`
- 預覽視窗固定顯示橫式或直式取決於實際呈現比例：因為顯示頁是全螢幕輪播（見下方「顯示頁」章節），公告呈現比例與 screen13（1080×2160 直式）相近，預覽固定用直式模式即可，不需橫式切換

### 房間清單維護

會議室預約分頁內加一個小區塊，可增減／改名／改容納人數 `meetings.rooms` 的 5 筆房間基本資料，不需改程式碼即可因應房間調整（例如日後房間整併、改名）。

## 顯示頁（`shared/roomBoard.js`）

### 版面：1080×1920 直立，全螢幕輪播

不採用「狀態常駐 + 下方小區塊輪播公告」的固定分割版面（該版面會讓公告顯示區域偏擠）。改為**整頁在多張全螢幕投影片之間輪播**，狀態頁本身是其中一張投影片：

```
狀態頁 → 公告1 → 狀態頁 → 公告2 → 狀態頁 → 公告3 → …（循環）
```

狀態頁**穿插在每一則公告之間**（而非跑完所有公告才回到狀態頁一次），確保不論公告則數多寡，路過的人最多等一則公告的時間就會再看到一次房間狀態。

**狀態頁內容**（全螢幕）：
```
🏢 會議室 A（40人）
      14:32:07                ← 即時時鐘，每秒更新

      【使用中】
      管委會議
    14:00 ~ 15:30

  ─ 今日剩餘預約 ─
  15:30-16:00  住戶大會
  17:00-18:00  訪客座談
```
- 「今日剩餘預約」列出今天「結束時間還沒到」的預約（`date === 今天 && endTime > 現在時間`），依 `startTime` 由早到晚排序，包含正在進行中與待會才開始的
- 因為狀態頁現在是全螢幕呈現，空間寬裕，列表上限放寬到約 6 筆（純粹是防呆用的上限，不是版面擠壓考量），超過就不再往下列
- 沒有剩餘預約時，「今日剩餘預約」整段不顯示

**公告頁內容**（全螢幕）：呈現方式比照既有 screen13（1080×2160 直式公告）的做法，含標題／內容／圖片。

**停留時間**：
- 狀態頁固定 8 秒
- 公告頁採用該則公告資料的 `duration` 欄位（管理員可各別設定，預設 7 秒），與既有公告輪播行為一致

### 資料讀取與即時更新

- 初始化：`window.ghBackup.autoRestore()` → `window.api.get('meetings')` + `window.api.get('meetingAnnouncements')`
- 狀態每分鐘重新計算一次（不需整頁重新整理即可反映預約開始/結束）
- 監聽 `meetings:updated`／`meetingAnnouncements:updated`：管理後台存檔後，門口螢幕於 1 分鐘內背景輪詢偵測到更新並自動套用（沿用本次已修好的 admin 端同一套自動刷新機制的對應設計）
- 保留既有專案慣例的 `<meta http-equiv="refresh">` 當保底

### 找不到房間的防呆

若 `meetings.rooms` 裡找不到對應 `ROOM_ID` 的房間（例如後台刪除了某間房，但門口螢幕網址還沒改），顯示明確的提示文字，不整頁報錯卡死。

## 部署

5 台門口螢幕硬體已存在（先前指向舊系統），本次不需更動機器本身，僅需把每台螢幕目前指向的網址，從舊系統 `172.18.0.251/.../room0X.html` 改成對應的新網址（例如 `.../renderer/room-a/`），5 台各自對應 1 個房間 ID。

## 測試與驗收

- 本機用假預約資料測試：一筆進行中、一筆待會開始、一筆已過期，確認「使用中/未使用」判斷正確、「今日剩餘預約」只列出未過期的、依開始時間排序
- 確認管理後台新增預約時，同房間重疊時段會被擋下
- 確認公告編輯器存檔到 `meetingAnnouncements` 時不會誤存或污染既有的 `announcements`／`announcements_v`
- 5 個入口檔案各自帶不同 `ROOM_ID` 開啟，確認只顯示對應房間的狀態、不會抓錯房間
- 確認輪播順序正確（狀態頁穿插在每則公告之間）、各投影片停留時間符合設定
- 確認找不到房間時的防呆畫面正常顯示，不會整頁報錯
