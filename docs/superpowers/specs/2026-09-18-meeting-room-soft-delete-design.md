# 會議室預約軟刪除設計

日期：2026-09-18

## 背景

管理後台會議室預約分頁的「刪除」目前是直接把該筆預約從 `meetings.bookings` 陣列移除並存檔（`deleteBooking()`），沒有任何緩衝或復原機制。使用者反饋：手滑刪錯、或刪除後反悔想恢復時，目前完全無法挽回。希望改成軟刪除：刪除後先反灰保留 7 天，讓管理員有機會復原，7 天後才真正永久刪除。

這是純靜態網站（GitHub Pages），沒有後端伺服器、沒有排程系統，「7 天後真的刪除」這件事無法用背景工作跑，只能靠使用者端某個時機主動檢查並清除過期資料。

## 目標

- 刪除預約時先軟刪除（標記 + 反灰），保留 7 天緩衝期
- 緩衝期內可以復原，也可以選擇立即永久刪除（不用等 7 天）
- 緩衝期內該時段釋放給其他新預約使用（避免占著茅坑）
- 復原時要重新檢查時段是否已被新預約佔用，避免復原出衝突
- 過期（超過 7 天）的軟刪除項目，在進入「會議室預約」分頁時自動真正清除
- 5 台門口螢幕的顯示邏輯（`shared/roomBoard.js`）要跟著排除軟刪除的預約，不能顯示已刪除的預約為使用中或列入今日剩餘預約

## 非目標（本次不做）

- 不做軟刪除歷史紀錄/稽核軌跡（誰在什麼時候刪除/復原），只保留 `deletedAt` 一個時間戳記
- 不做月曆格子上顯示軟刪除項目的灰色色塊，月曆格子完全不計入軟刪除預約
- 7 天緩衝期長度不做成可設定選項，寫死 7 天
- 不處理「進入會議室預約分頁以外的時機」的自動清除（例如頁面待機很久都沒人切分頁），這是純靜態網站的已知限制，使用者已接受

## 資料結構變更

### `meetings.bookings` 新增一個欄位

```js
{
  id: 1758...,
  roomId: 'A',
  date: '2026-09-20',
  startTime: '14:00',
  endTime: '15:30',
  topic: '管委會議',
  person: '王小姐',
  tenant: '4A - 威傑士國際開發有限公司',
  paid: true,
  deletedAt: '2026-09-18T10:30:00.000Z'  // 新增：軟刪除標記，ISO 時間字串。沒有這個欄位（undefined）＝正常有效預約
}
```

- `deletedAt` 不存在或為 `undefined` → 這是一筆正常有效的預約
- `deletedAt` 存在且距今不超過 7 天 → 軟刪除中，緩衝期內，反灰顯示可復原
- `deletedAt` 存在且距今超過 7 天 → 下次進入會議室預約分頁時會被真正清除，不會再出現在任何畫面

## 行為變更

### 1. 刪除（`deleteBooking`）

點擊刪除時的確認訊息改為：「確定要刪除這筆預約嗎？（會保留 7 天，期限內可復原）」。確認後**不再**從陣列移除該筆資料，而是設定 `booking.deletedAt = new Date().toISOString()`，存檔、重新渲染月曆與當天明細、觸發備份。

### 2. 時段釋放（重疊檢查排除軟刪除項目）

`saveBooking()` 的重疊檢查（`bookingOverlaps`）在比對既有預約時，要排除 `deletedAt` 存在的項目——軟刪除中的預約不再佔用時段，同一時段可以被新預約使用。

### 3. 當天明細列表（`renderBookings`）反灰顯示

每間房間的卡片內：
- 正常有效的預約（無 `deletedAt`）照現有樣式顯示（含既有的未繳費紅框警示）
- 軟刪除中的預約（`deletedAt` 存在且未過期）另外列在該房間卡片內、正常預約之後，用反灰樣式呈現（例如降低透明度、灰色文字），顯示「已刪除（還剩 N 天後永久移除）」的字樣（N 從 7 往下算，`Math.ceil((7*24*60*60*1000 - (現在時間 - deletedAt)) / (24*60*60*1000))`），並提供兩個按鈕：**[復原]**、**[永久刪除]**
- 月曆格子的色塊與未繳費紅框判斷完全不計入軟刪除中的預約（等同該預約在月曆總表上「已經不存在」）

### 4. 復原（新增 `restoreBooking(id)`）

點擊「復原」：
1. 找到該筆預約，先檢查它的時段是否已被其他「目前有效（無 `deletedAt`）」的預約佔用（用既有 `bookingOverlaps()` 邏輯，排除自己）
2. 若有衝突 → 用 `toast(..., 'error')` 提示「這個時段已經被別的預約佔用了，請先調整時間再復原」，不執行復原
3. 若無衝突 → 清除該筆的 `deletedAt`（`delete booking.deletedAt` 或設為 `undefined`），存檔，重新渲染月曆與當天明細，觸發備份，顯示成功提示

### 5. 永久刪除（新增 `hardDeleteBooking(id)`）

只能對「已經軟刪除中」的項目使用，點擊「永久刪除」會再次 `confirm()`（文案：「確定要永久刪除這筆已刪除的預約嗎？此動作無法復原。」），確認後才真正從 `meetings.bookings` 陣列移除、存檔、重新渲染、觸發備份。

### 6. 過期自動清除（新增 `purgeExpiredBookings()`）

在 `showTab('meetings')` 分支被呼叫時（也就是每次管理員切換到「會議室預約」分頁），先執行一次：掃過 `meetings.bookings`，找出 `deletedAt` 存在且距今超過 7 天（`Date.now() - new Date(b.deletedAt).getTime() > 7*24*60*60*1000`）的項目，從陣列移除。若確實清掉了至少一筆，才觸發 `window.api.save('meetings', meetings)` 與 `triggerBackup()`（避免每次切分頁都做不必要的寫入）。這一步在 `renderRoomList()`/`renderCalendar()`/`renderBookings()` 之前執行，確保後續渲染看到的是已經清乾淨的資料。

### 7. `shared/roomBoard.js` 排除軟刪除預約

`computeRoomState(meetings)` 目前用 `roomId`/`date` 篩選出當天預約後計算「使用中」跟「今日剩餘預約」，這次要在篩選條件裡加上排除 `deletedAt` 存在的項目，避免已被管理員刪除（即使還在 7 天緩衝期內）的預約繼續在門口螢幕上顯示為使用中或列在剩餘預約清單裡——門口螢幕是給訪客看的即時狀態，不應該讓已刪除的預約誤導訪客。

## 測試與驗收

- 刪除一筆預約後，確認它從月曆格子的色塊消失，但在當天明細列表以反灰樣式出現，帶正確的「還剩 N 天」文字
- 確認軟刪除中的時段可以被新預約使用（不會被舊的重疊檢查擋下）
- 復原一筆軟刪除的預約，確認它恢復正常顯示、月曆格子色塊重新出現
- 復原一筆時段已被新預約佔用的軟刪除預約，確認被正確擋下並顯示錯誤提示，資料不會被復原
- 對軟刪除中的項目按「永久刪除」，確認立即從資料中消失，不用等 7 天
- 模擬一筆 `deletedAt` 是 8 天前的軟刪除預約，切換到「會議室預約」分頁後確認它被自動清除、不再出現在任何地方
- 確認一筆 `deletedAt` 是 3 天前（尚未過期）的軟刪除預約，切換分頁後不會被清除，仍正常顯示在反灰列表
- 用假的 `meetings` 資料（含一筆軟刪除但未過期的預約）餵給 `shared/roomBoard.js` 的 `computeRoomState()`，確認回傳結果不包含該筆軟刪除的預約（不算進使用中、不算進今日剩餘預約）
